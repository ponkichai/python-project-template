# プロジェクト開発方針

## ディレクトリ構造

| パス | 役割 |
|------|------|
| `src/` | アプリケーションコード（Configを持たない） |
| `tests/` | テストコード |
| `config/` | 設定ファイル（環境ごとに異なる値） |
| `specs/` | 機能仕様書（実装前に書く） |
| `.claude/skills/` | このプロジェクト固有のスキル |

## 開発フロー（SDD → TDD → AIDD）

新機能を追加する際は必ずこの順序で進める。

### 1. Spec を書く（SDD）
`specs/<機能名>.md` を作成し、以下を定義する：
- 入力・出力・仕様・除外スコープ
- `/new-feature` スキルを使うと対話形式でspecを作れる

### 2. テストを先に書く（TDD）
- `tests/test_<機能名>.py` を specから作成
- この時点では全テスト失敗してよい
- 正常系・異常系を網羅する

### 3. AIに実装させる（AIDD）
- spec + テストコードを渡して実装を生成
- `make test` で検証 → 失敗したらエラーをフィードバック

## Code / Config 分離ルール

- パス・パラメータ・フラグは `config/*.yaml` に書く
- `src/` のコードに値をハードコードしない
- APIキー等の機密情報は環境変数から取得する（YAMLにも書かない）

## コード品質

```bash
make lint        # Ruff lint + format（自動修正）
make type-check  # Ty 型チェック
make test        # pytest（カバレッジ付き）
make check       # 上記すべて
```

コミット時に pre-commit hook が自動実行される。
失敗した場合はコミットが中断されるので、エラーを修正してから再コミットする。

## 禁止事項

- `config/local.yaml` や `.env` をコミットしない（.gitignore済み）
- テストをスキップして `--no-verify` でコミットしない（緊急時のみ）
- `src/` に設定値をハードコードしない
